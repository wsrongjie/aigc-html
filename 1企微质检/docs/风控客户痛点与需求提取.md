# 风控客户痛点与需求提取

> 分析日期：2026-10-23  
> 资料范围：4 份客户访谈转写 + 2 份当前 SaaS 系统梳理  
> 目标：提取金融投顾业务中与风控、合规、客诉、质检和内容审核有关的现状、痛点与需求，为后续产品设计提供依据。

## 1. 核心结论

客户当前最急迫的问题不是“再增加一个风险列表”，而是把已经存在的大量风险线索变成**准确、可追溯、能闭环的风险事件**。

从一线工作看，当前存在四个连续断点：

1. **发现不准**：主要依赖敏感词，无法理解上下文、语音情绪、图片符号和表达语境，误报量极大。
2. **证据难找**：聊天、文字直播间、视频直播、小程序行为、订单、退款、合同和外呼等信息分散，合规人员需要跨系统手工拼接。
3. **处置费力**：风险确认、通知销售、销售处理、合规复核、结案跟踪仍是系统与线下台账混合运行。
4. **尺度难固化**：总部要求、公司阶段、市场行情、产品等级、内容用途和落地场景都会改变审核尺度，无法靠一套静态词库解决。

合规受访者明确希望：**先把客户投诉降下来，解决眼前最痛的问题。**本文据此建议优先处理客诉识别、取证与跟踪；员工质检、素材审核和客户分级的先后顺序仍需甲方负责人确认。

## 2. 当前风控业务全景

### 2.1 四条风控业务线

| 业务线 | 当前工作 | 当前主要载体 |
| --- | --- | --- |
| 客诉与退款风险 | 从企微沟通中识别外诉、投诉、退费、亏损和抱怨，通知业务处理并由合规复核 | 合规系统、订单系统、企微通知、Excel 台账 |
| 员工质检稽核 | 根据业务合规制度核查销售沟通是否违规，形成整改说明、罚单、签字、总部报送和人事扣款 | 敏感词列表、违规列表、人工复核、线下协同 |
| 营销内容审核 | 审核销售、策划和自媒体的文字、图片、视频、直播观点、个股验证等内容 | 企微审核群、素材系统、股票备案与直播审核页面 |
| 交易与履约合规控制 | 实名、风险测评、购买/回访/退款合同、服务开通、对公转账与退款出款 | 订单系统、合同/OCR、实名与财务审核页面 |

其中前三条是访谈中反复出现的主要痛点。第四条是完整风控边界中不可遗漏的控制线，但访谈认为实名和适当性当前压力较小；现有页面只证明相关入口和状态存在，不能反推出审核、签约、服务开通和出款之间已形成强制依赖。

### 2.2 当前客诉处理流程

现有流程大致为：

`敏感词触发 → 合规待确认 → 标记风险类别和截止时间 → 企微通知销售/主任 → 销售安抚或退款 → 合规查看上下文、订单和退款状态 → 复核 → 完结或延期`

访谈中还提到几项明确机制：

- 受访者描述 T0 外诉风险需当天处理，未处理则介入退费。
- 同一客户重复触发需要前后关联，不能按孤立事件判断。
- 客户重复触发三次、拨打 400 电话三次或三个工作日未妥善处理，涉及强制介入或退费；但客户情绪缓和、已达成一致时存在人工延期空间。精确计数与适用条件仍需制度文档核对。
- 合规人员会把高危客户导出为 Excel 台账，再同步给主管跟进。

这说明客户已有制度与部分线上流程，缺少的是更准确的识别、跨系统取证和自动化闭环，而不是从零设计一套客诉制度。

## 3. 访谈提取的核心痛点

### 痛点 1：敏感词产生海量误报，人工无法处理

**客户事实**

- 合规侧已有约 8 万多条咨诉触发记录；员工违规触发记录达到约 180 万条。
- “监管”可能出现在正常市场评论里，“退”也可能出现在与退款无关的日常表达里，纯文本匹配无法判断真实意图。
- 抱怨类任务量过大，合规人员曾直接停掉相关类别，触发量随即减少近一半。
- 过去尝试使用通用 AI，结果尺度过严、几乎全部判违规，失去业务价值。

**痛点本质**

不是风险线索不足，而是**信噪比过低**。如果把所有疑似问题都交给销售或合规，系统本身会制造新的工作负担。

**客户期望**

- **客户明示**：结合上下文、制度定义和关键词做综合判断。
- **客户明示**：宁可前期只筛出少量高度明确的问题，也要保证准确，避免消耗销售精力。
- **访谈讨论认可**：对投诉、退款、抱怨、外诉等意图先做轻量筛选，再由大模型二次判断。

**证据**：`合规访谈.md:28-40, 70-76, 100-106`；`产品团队.md:517-553, 865-900`。

### 痛点 2：风险证据散落在多个系统，核实一个事件耗时很长

**客户事实**

当前访谈明确描述的人工核查包括聊天上下文、订单及退款处理结果。客户另希望综合纳入直播间沟通、观看和小程序点击等行为；这些数据的覆盖、关联和实际取证能力仍需核实。

- **当前明确核查**：企微聊天上下文、订单、退款申请、审批和系统显示的退款处理结果。
- **希望纳入判断**：文字直播间发言、视频直播观看、小程序点击、客户历史风险表述及销售给出的仓位或操作提示。
- **待核实覆盖**：群聊、企微语音、外呼/400 电话、合同、回访和服务状态等数据能否完整关联到同一风险事件。

访谈中的“退款成功”是系统页面所示处理结果，不代表本次已经核验银行实际到账。

访谈中直接提到“找记录不好找”“证据链不好找”，并已向内部技术提出点击客户即可查看全部沟通记录的需求。

**痛点本质**

当前系统以业务模块保存数据，但风控工作需要以**客户风险事件**为中心组织证据。数据存在不等于证据可用。

**客户期望**

- **客户明示**：从风险事件一键进入客户完整上下文。
- **访谈讨论认可**：自动汇总跨系统证据，并显示命中规则、风险原句、上下文、订单/退款进展、客户情绪和销售处置结果。
- **客户明示**：综合客户历史行为和员工沟通记录判断责任，避免只凭单段聊天处罚员工。

**证据**：`合规访谈.md:52-70, 76-97, 340-355`；`订单管理系统功能梳理.md:94-104, 184-210`。

### 痛点 3：风险处置仍依赖人工拼接和线下台账，闭环效率低

**客户事实**

- 系统虽然已有待确认、处理中、待复核、已完结、逾期和延期等状态，但实际仍是线上与线下混合运行。
- 合规需要人工判断、给建议、指定处理时间、导出台账、催促业务，再回查聊天和退款结果。
- 员工违规后续还包括沟通、整改说明、罚单签字、总部报送、人事扣款和培训宣导。
- 现有系统的部分风险记录只能关闭，无法完成完整的处置流程；另一个功能虽形成了闭环，但仍高度依赖人工。

**痛点本质**

风险识别、任务派发、业务处置、证据回流和合规复核没有形成统一事件模型，导致过程状态与实际结果容易脱节。

**客户期望**

- **客户明示**：风险生成任务并分配给对应销售或负责人跟进。
- **客户明示**：支持处理时限、逾期、延期、升级和强制介入机制。
- **访谈讨论认可**：销售提交处理说明和证据，合规聚焦人工复核。
- **客户明示**：客户重复触发时关联历史事件，不重新从头判断。

**证据**：`合规访谈.md:40-70, 130-145, 190-208`；`产品团队.md:772-805`；`客户后台合规系统SaaS功能梳理.md:64-81`。

### 痛点 4：文字直播间负面信息量大，路由慢且责任边界模糊

**客户事实**

- 文字直播间会通过关键词拦截负面发言，但被拦截的内容未必及时同步给对应销售和投顾老师。
- 当前压力主要给到直播间的头部老师，合规部门没有能力处理全部过程。
- 客户认为人工同步较慢，估计“半小时已经是乐观情况”，但也明确表示不确定实际时长；“可能未同步”是访谈中提出的可能性，尚无时效测量或具体案例佐证。
- 同一客户可能同时关联多个销售和多个直播间老师，风险信息应该发给实际相关人员。

**痛点本质**

系统识别了风险消息，却没有可靠的**客户—直播间—投顾老师—销售人员**关系来完成实时路由。

**客户期望**

- **客户明示**：将被拦截的负面内容自动同步给相关销售和投顾老师。
- **客户明示**：同时给出客户身份、抱怨内容、风险级别、建议安抚策略和参考话术。
- **产品建议**：重要风险汇总进入合规客诉队列，由合规查看结果而非人工盯住全部直播过程。

**证据**：`合规访谈.md:226-250, 255-316`。

### 痛点 5：营销素材审核依赖群聊，尺度动态且高度语境化

**客户事实**

- 所有营销内容原则上先审后发，图文、视频、销售素材、策划素材和自媒体内容主要在企微审核群内流转。
- 不同产品层级（1.0/2.0/3.0）、内容用途、市场行情和公司阶段，对应不同审核尺度。
- 同一个主标题单独使用可能通过，与个股验证、客户盈利或强刺激视觉组合后可能不通过。
- “牛股、黑马股”等禁止说辞可以换词、造词，也可以通过火箭、金元宝、红底黄字、字号和重复次数形成过度渲染，单纯 OCR 或关键词无法识别。
- 目前审核结果多为通过/不通过，修改建议不足。

**痛点本质**

素材风险不是单字段规则问题，而是**内容、视觉、上下文、使用场景和当前审核策略共同决定的多模态判断**。

**客户期望**

- **访谈讨论认可**：支持文字、图片、视频和直播内容的多模态审核。
- **客户明示**：除了通过/不通过，还要提供修改建议；访谈进一步讨论了风险定位、规则解释和保持原意的改写。
- **产品建议**：正式制度、审批后的场景策略、模型阈值和临时例外分别管理，不能混成一个“松紧尺度”；冲突时记录裁定人、依据、生效时间和到期时间。
- **产品建议**：保留送审版本、审核意见、修改版本、审核人和最终发布版本，便于追溯和训练。

**证据**：`合规访谈.md:358-400`；`营销策划-1队.md:37-58, 97-139`；`营销策略-2队.md:34-61`；`产品团队.md:121-187, 1248-1269`。

### 痛点 6：员工违规质检规模大，但缺少精准分层和持续训练机制

**客户事实**

- 公司总部有业务合规管理制度，本地团队会把部分条款转成敏感词监控，再人工复核、处罚。
- 总部规则与本地经营目标可能存在尺度冲突，执行过程中会阶段性放宽或收紧。
- 客户不希望一次性把大量模糊问题推给销售，而是先处理确定性高、后果严重的问题。
- 客户认可人工复核、结果标记与效果评测。现有罚单及案例材料的覆盖范围、结构化程度和正负案例完整性仍待合规部门确认；合规受访者愿意按约定格式准备案例。

**痛点本质**

静态词库只能发现字面命中，无法表达违规严重度、业务容忍度和模型可信度，也无法通过人工复核结果形成学习闭环。

**客户期望**

- **客户明示**：风险分类、分级并优先推送高确定性事件。
- **访谈讨论认可**：人工标记误判、确认违规、风险片段和正确分类。
- **访谈讨论认可**：将复核结果沉淀为评测与训练数据，对比模型与人工判断的一致性。
- **产品建议**：展示模型版本、规则版本、命中依据和历史效果，支持发布、回滚与持续调优。

**证据**：`合规访谈.md:100-145, 397-423`；`产品团队.md:187-217, 292-343`。

### 痛点 7：客户风险目前以标签和黑名单为主，缺少精细分级

**客户事实**

- 当前企微侧已有敏感职业、高危客户、辱骂、外部投诉风险等标签。
- 紧急能力主要是黑名单、禁止成交或屏蔽群发。
- 客户明确认为应该进一步形成风险一级、二级、三级，但受工作量、排期和跨部门协同限制没有落地。
- 外部异常客户还可能来自手机号黑名单、重复添加、同行或记者等来源。

**痛点本质**

二元黑名单只能处理极端风险，不能支持差异化营销、服务、审核、复购和触达策略。

**客户期望**

- **客户明示**：建立比黑名单更精细的风险一级、二级、三级分类。
- **产品建议**：风险等级与下单拦截、群发屏蔽、人工确认、服务策略和事件升级联动。
- **客户明示**：该能力需要销售、合规和产品多部门协同；具体维护权责仍待确认。

**证据**：`合规访谈.md:429-459`；`产品团队.md:322-343, 382`；`客户后台合规系统SaaS功能梳理.md:83-106`。

### 痛点 8：人员、账号和组织关系维护成本高，影响责任归属

**客户事实**

- 一个员工可能拥有多个企微账号，账号名称与员工真实姓名不一致。
- 员工与企微账号的映射目前依靠人工维护。
- 风险任务需要知道员工所属事业部、团队、主管以及实际服务客户，才能正确通知和统计责任。
- 产品技术受访者称会话存档在 5 分钟内同步；这不等于 AI 风控也具备相同时效，模型分析批次、端到端延迟和数据覆盖率仍需验证。

**痛点本质**

如果人员主数据不稳定，风险数量、责任团队、客户归属和绩效统计都会失真。

**客户期望**

- **客户明示**：接入统一组织架构和人员接口，并处理员工与多个企微账号的映射。
- **产品建议**：建立员工稳定 ID 与多个企微账号 ID 的长期映射，避免以姓名关联。
- **产品建议**：风险事件以稳定客户 ID、员工 ID、企微账号 ID、消息 ID 和业务对象 ID 关联。

**证据**：`产品团队.md:37-112`。

## 4. 需求提取与产品化表达

| 原始诉求 | 来源性质 | 建议产品能力 | 验收方向 |
| --- | --- | --- | --- |
| 准确识别投诉、退款、抱怨、外诉意图 | 客户明示；两阶段识别为讨论认可 | 轻量意图召回 + 大模型上下文复判 + 置信度阈值 | 高风险事件精确率、漏报率、人工复核量 |
| 点击客户即可看到全部记录 | 客户明示 | 客户 360 风险档案与统一事件时间线 | 单次调查跨系统跳转数、平均取证时间 |
| 自动整理证据链 | 访谈讨论认可 | 规则命中、原句、上下文、语音转写、情绪、订单/退款/合同状态聚合 | 证据完整率、证据回跳成功率 |
| 只把精准问题给销售 | 客户明示 | 风险分级、推送阈值、静默观察区、人工复核队列 | 每百条推送有效数、销售无效任务量 |
| 识别后生成任务并跟进 | 客户明示 | 指派、截止时间、催办、延期、升级、复核、结案 | 按时处理率、平均结案时长、逾期存量 |
| 重复触发要前后关联 | 客户明示 | 客户风险事件聚合和复发机制 | 重复事件合并准确率、复发识别率 |
| 直播间负面内容同步相关人员 | 客户明示 | 客户—直播间—投顾—销售关系路由 | 通知送达率、首次响应时长 |
| 素材不仅判断，还要告诉怎么改 | 客户明示 + 讨论认可 | 多模态风险定位、规则解释、改写建议、版本对比 | 修改后一次通过率、平均审核轮次 |
| 不同阶段使用不同尺度 | 客户描述现状；治理方式为产品建议 | 正式制度、场景策略、阈值、临时例外分层治理 | 冲突有裁定、策略可追溯、历史结果可复现 |
| 人工复核并反哺模型 | 访谈讨论认可；版本治理为产品建议 | 标注台、评测集、效果看板、模型发布与回滚 | 人机一致率、误报变化、版本回归结果 |
| 客户风险要分级 | 客户明示；业务联动为产品建议 | 客户风险画像、动态等级和业务策略联动 | 分级覆盖率、拦截/人工确认命中率 |

## 5. 建议的优先级（待甲方确认完整排序）

只有“近期优先降低投诉”属于客户明确表达；以下四阶段顺序是产品建议，不代表甲方已经确认排期。

### 第一阶段：客诉风险闭环（最高优先级）

目标是直接减少投诉风险与人工取证成本。

1. 打通客户、员工、企微账号、消息、直播间、订单、退款和合同的稳定关联。
2. 对客户消息做投诉、退款、抱怨、外诉意图识别；普通批量普查的周期尚待确认，T0 外诉和直播间即时风险需分别定义识别时效、通知时效与处置截止，不能被离线普查替代。
3. 形成客户风险事件，自动聚合近 10—15 天上下文及业务状态。
4. 提供合规复核台：风险依据、证据链、情绪、建议、负责人、截止时间和处置结果同屏呈现。
5. 支持任务派发、催办、延期、升级、复核、完结和重复触发关联。

### 第二阶段：员工违规质检

目标是从 180 万级字面命中中筛出高确定性违规。

1. 将制度条款结构化为风险分类、严重等级、判断条件和反例。
2. 建立人工复核与标注闭环。
3. 先上线少量高精度规则，低置信度内容进入静默评测，不直接打扰销售。
4. 接入罚单、整改、签字、总部报送和人事执行的过程留痕。

### 第三阶段：营销素材审核

目标是降低群内审核压力，提高一次通过率。

1. 建立统一送审入口和素材版本链。
2. 支持文字、图片、视频、语音和视觉元素联合审核。
3. 输出风险定位、理由和可执行修改建议。
4. 按产品、渠道、用途、行情和时间维护审核策略版本。

### 第四阶段：客户风险分级与前置防控

目标是从事件响应升级到客户全生命周期风险控制。

1. 建立动态风险等级及变化原因。
2. 联动成交、群发、直播发言、服务、复购和退款策略。
3. 区分员工责任、客户责任、市场原因和未确定责任。

### 能力成立的权限前提

跨系统证据聚合不等于扩大数据可见范围。MVP 必须继承来源系统的企业、组织和角色权限；聊天原文、录音、证件、手机号、订单金额等敏感信息应按角色脱敏；授权调阅、查看、导出、转派和下载均需留痕。具体保存期限、审批链和字段级权限仍需甲方确认。

## 7. 当前资料仍未回答的问题

这些问题会直接影响下一步原型和系统设计，需要甲方补充：

1. **正式制度材料**：业务合规管理制度、咨诉结案机制、客诉规范、适当性要求、禁止说辞和素材审核规则。
2. **正负案例格式**：通过、不通过、误判、模糊案例分别需要哪些字段；原始案例是否允许脱敏后用于评测。
3. **风险优先级与分析周期口径**：访谈同时出现 T0、P0、L0/L1/L2 及“T 减一”等说法，需要统一业务术语、等级顺序、分析周期和处置时限，不能擅自将“T 减一”改写为 T+1。
4. **强制退费规则**：“三次、三个工作日、三次 400 电话”的精确定义、例外条件和审批权限。
5. **责任路由**：客户同时关联多个销售、多个企微账号和多个投顾老师时，主责与协同人员如何确定。
6. **数据主键映射**：企微联系人、订单用户、直播间用户、小程序用户和手机号之间目前如何关联，历史数据缺失率如何。
7. **数据覆盖率**：企微消息、语音电话、群聊、直播评论、外呼录音分别能保存哪些内容，保存期限和同步失败补偿机制是什么。
8. **权限与审计**：谁能查看聊天原文、录音、身份证、订单和投诉证据；导出、转派和查看是否需要审计。
9. **效果基线**：当前每天/每周触发量、有效量、误报率、平均处理时长、逾期率、投诉率和退款率。
10. **素材策略负责人**：总部规则与本地临时尺度冲突时，谁有最终决定权，临时策略如何留痕和到期失效。

## 8. 需求边界说明

- “8 万多条”“180 多万条”及其他百万级记录均为受访者口述，尚未通过生产数据核验。“一天 1000 万条、客户消息占 2%—5%”是受访者用于说明筛选思路的假设示例，不作为真实规模或容量依据。
- 现有 SaaS 梳理来自测试环境的只读页面观察，只证明界面存在相应字段或入口，不证明后台流程、权限、模型效果和生产数据同步已经验证。
- “小模型识别 + 规则结合大模型复判 + 任务跟进”由客户产品技术受访者主动提出；按行情区分 L1/L2/L3 模型等实现方式由访谈发起方提出。两者均尚未形成最终实施方案。
- 本文将“客户明确说出的工作问题”和“产品化归纳”分开表达；优先级为基于访谈紧迫度作出的建议，最终仍需甲方业务负责人确认。
