# 客户当前合规 SaaS 设计评审

> 分析日期：2026-10-23  
> 主要依据：`客户当前saas系统梳理/客户后台合规系统SaaS功能梳理.md`  
> 交叉依据：`docs/风控客户痛点与需求提取.md`  
> 分析边界：当前资料来自测试环境只读观察，只能确认页面、字段和入口；不能据此确认生产流程、接口、权限、模型效果和数据完整性。

## 1. 当前结论

### 明确判断

这套系统**值得保留，并应优先核实其作为业务执行底座的可行性**。从当前页面证据看，它不足以直接证明可以承担未来 AI 风控中枢的全部职责；最终集成方式取决于现有接口、状态机、权限和生产数据验证结果。

它已经覆盖 9 个一级模块、35 个二级入口，具备较完整的合规业务“零件”：

- 企微会话存档、授权调阅和关键词检索；
- 敏感词、敏感行为和客诉预警；
- 咨诉、违规、投诉、退款风险等列表；
- 异常客户、黑名单和拦截记录；
- 投顾/从业人员、呼叫中心和订单查询；
- 股票备案、素材送审、直播审核和产品活动。

从页面信息架构看，系统更像多个历史需求叠加形成的**功能集合**；底层是否已经围绕统一风险事件形成闭环尚未得到证明。现有资料也不能证明它能稳定完成：

`多源信号识别 → 风险事件聚合 → 证据链生成 → 责任人路由 → 处置协同 → 人工复核 → 结案/复发 → 模型学习`

因此，当前建议不是重做原 SaaS，也不是继续往侧边栏增加孤立菜单，而是先验证原有对象和状态机；若缺少统一工作入口，再增加一个**AI 风控工作视图或服务层**。数据资产中心提供统一索引和稳定标识，原系统是否作为数据来源、任务主存和结果回跳目标，必须经接口及生产流程核实后确定。

### 判断置信度

**中等。**页面信息架构和字段证据充分，但真实状态流转、角色权限、数据覆盖率和模型效果均未执行验证。

## 2. 当前系统设计的实际分层

从现有页面可以将系统还原为五层：

| 层级 | 当前模块 | 页面已体现的信息 | 当前局限 |
| --- | --- | --- | --- |
| 数据采集与调阅 | 沟通留痕、呼叫中心、订单列表 | 会话、通话、订单查询；员工/客户视角；授权调阅 | 采集覆盖率、跨源身份关联、保留期限和回跳完整性未验证 |
| 风险发现 | 敏感词、敏感行为、客诉预警、退款预警 | 规则触发、风险原句、评分、置信度、情绪摘要等字段 | 以关键词页面为主；退款预警当前列表为空，其他列表的 AI 分析覆盖情况未确认 |
| 风险判断与任务 | 咨诉列表、违规列表、投诉处理、合规看板 | 分类、上下文、处理状态、截止时间、复核/完结状态 | 多套对象并存，是否共享同一事件和状态机不明 |
| 风险处置 | 通知设置、异常客户、购买拦截、处理入口 | 通知对象配置、客户类型/等级字段、支付与直播场景的拦截记录展示 | 实际通知、拦截、指派、升级、复发、解除和跨系统联动未验证 |
| 前置内容合规 | 股票备案、素材送审、直播审核、产品活动 | 股票/素材/直播的送审或审核字段；产品活动的审核状态字段 | 产品活动审核动作、版本链、退回修改、发布控制和多模态审核细则不明 |

该设计说明甲方并非从零开始：页面上已经出现数据入口、分类词库、任务状态和拦截记录。下一步应先验证这些层之间是否已有统一对象和闭环关系，再决定复用、扩展还是新建。

## 3. 当前设计做得较好的部分

### 3.1 会话调阅具备较好的数据入口基础

员工会话存档、员工授权调阅和客户会话存档同时存在，并支持员工/客户、群聊、日期、关键词等维度。这与客户需要的双向查看方式基本一致，是应优先验证的复用候选。

优先核实并评估复用：

- 原始消息和会话查询入口及可能的开放接口；
- 员工、客户、群聊和时间筛选能力；
- 授权调阅概念；
- 原始记录导出入口及可能的记录回跳能力。

接口开放方式、生产数据完整性、授权约束、导出范围和原始消息回跳均未验证，暂不认定其为权威数据源或可直接复用的接口。

依据：原梳理第 24—42 行。

### 3.2 已经出现风险任务闭环的雏形

咨诉和违规列表包含流程 ID、分类、员工、事业部、AI 分析、任务触发时间、截止时间、完成时间和状态；看板又提供待确认、处理中、逾期、待复核、延期和已完结等状态。

这意味着原系统的数据结构可能已经具备“线索转任务”的部分基础，后续应优先核实和复用，而不是另外再造一套完全独立的任务状态。

依据：原梳理第 64—81 行。

### 3.3 客户风险控制已经能表达名单与拦截

系统已有异常客户、外部异常客户和拦截记录；拦截场景包含支付下单、文字直播间和视频直播间。这为未来客户风险分级与业务策略联动提供了落点。

需要注意：当前只能确认页面展示这些记录，不能确认拦截是否实时、规则是否统一，以及解除风险后是否能自动恢复。

依据：原梳理第 83—106 行。

### 3.4 前置内容审核覆盖面较广

股票报告、诊股、素材和直播页面具有不同程度的送审或审核设计；产品活动只确认审核状态字段及添加入口，其送审、审核动作和层级尚未确认。对投顾行业而言，成交前的内容合规与成交后的客诉处置同样重要，原系统页面已经表达了这条业务线。

可优先评估复用：送审主体、组织、渠道、审核人、审核状态、审核日志和留痕状态等字段。

依据：原梳理第 130—165 行。

### 3.5 已经意识到组织、人员和权限维度

多个页面提供企业、组织、事业部、部门和员工筛选，同时存在授权调阅和部分字段脱敏。这是金融合规系统必须具备的基础方向。

但它目前只是“页面上出现了权限相关概念”，不代表租户隔离、字段级权限和审计已经验收。

依据：原梳理第 180—200 行。

## 4. 当前设计的核心结构性问题

### 问题 1：同一风险业务被拆成多套入口，用户难以判断去哪里处理

与客户投诉或退款相关的页面至少分布在：

- 沟通留痕 → 客诉预警；
- 风险控制 → 投诉处理；
- 风险控制 → 退款预警；
- 合规管理 → 咨诉列表；
- 合规管理 → 客户分类、咨诉分类；
- 客户管理 → 异常客户、拦截记录；
- 呼叫中心 → 订单列表。

这些页面可能分别表达“消息触发、AI 预警、投诉事项、处理任务、客户标签、业务拦截和交易状态”，业务上可以同时存在，但当前资料没有说明它们之间的统一关系：

- 哪个是原始信号；
- 哪个已经升级为风险事件；
- 哪个属于已认定的正式投诉；
- 哪个是执行任务；
- 哪个只是客户风险标签；
- 它们是否来自同一客户、同一原因和同一处置过程。

**设计风险**：如果底层没有统一关系，同一事件可能被重复处理，也可能在一个列表关闭后仍在另一个列表保持风险状态；是否已经发生需要通过真实流程验证。

### 问题 2：导航按历史功能和数据来源组织，而不是按用户任务组织

侧边栏把“沟通留痕、风险控制、合规管理、客户管理、呼叫中心”并列，但合规人员的真实工作不是依次进入五个菜单，而是围绕一个事件完成：发现、判断、取证、通知、处置、复核和结案。

**本质问题**：当前 IA 反映的是系统建设过程，而不是合规人员的工作流。

### 问题 3：统一风险事件详情尚未得到证明

现有列表字段已经很多，却没有证据证明存在一个页面能够同时展示：

- 风险类型、严重等级和置信度；
- 命中规则、风险原句和完整上下文；
- 语音、图片、视频和表情的结构化结果；
- 客户历史事件及重复触发；
- 订单、产品、合同、回访、退款和服务状态；
- 责任销售、企微账号、主管、投顾老师和协同人员；
- 销售回复、处置动作、客户后续情绪和实际结果；
- 人工复核、延期、升级和结案依据。

该缺口与访谈中“找记录不好找、证据链不好找”的现象高度相关，但是否为唯一根因仍需结合真实操作路径验证。

### 问题 4：触发记录、风险事件、任务和客户标签是否分层尚未确认

建议明确四类对象：

| 对象 | 定义 | 是否需要人工处理 |
| --- | --- | --- |
| 风险信号 | 单条消息、行为或模型输出的疑似风险 | 不一定，低置信度可静默观察 |
| 风险事件 | 同一客户、同一问题在一段时间内的信号聚合 | 需要判断和定级 |
| 处置任务 | 分配给销售、主管、投顾或合规的具体动作 | 需要按时完成和复核 |
| 客户风险状态 | 跨事件累积形成的客户当前风险等级 | 持续生效，可触发拦截或限制 |

当前页面名称已经涉及这四类含义，但没有证据表明底层模型真正分开。例如“疑似风险管理”页面实际呈现的是分类词库，不能据菜单名认定存在独立事件队列。

### 问题 5：风险发现仍主要依赖静态词库

员工敏感词、客诉预警、违规分类和咨诉分类都围绕词库展开。退款预警虽然出现评分、置信度和情绪摘要字段，但页面无数据，无法证明模型已实际运行。

与访谈对照，客户最痛的问题恰恰是关键词产生海量误报。因此，继续扩充词库不会从根本上解决问题，只会增加维护成本和触发量。

### 问题 6：现有看板更像状态汇总，不足以支持管理决策

当前看板可见咨诉和员工违规的状态数量，但尚未看到以下管理问题的答案：

- 本期新发生多少风险，当前还积压多少；
- 哪些部门、员工、产品和渠道风险最高；
- 误报率、人工确认率和复发率如何变化；
- 哪些事件逾期、为什么逾期、责任人是谁；
- 投诉是否减少，退款是否减少，处置是否真正有效；
- 哪个模型或规则版本导致风险量显著变化。

如果没有这些指标，管理层只能看到“列表里有多少条”，无法判断风险是否受控。

### 问题 7：规则配置缺少治理层

系统已有分类、词库、通知设置和监控范围，但未看到：

- 正式制度条款与内部经营策略的区分；
- 规则的适用产品、渠道、业务阶段和内容用途；
- 规则版本、生效时间、到期时间和审批人；
- 总部规则与本地临时策略冲突时的裁定记录；
- 模型阈值、灰度范围、评测结果和回滚；
- 人工误判/确认结果对规则和模型的反馈闭环。

这使动态审核尺度容易继续依赖个人经验，难以审计和复现。

### 问题 8：系统间存在业务视图重叠，数据共享与主数据关系待确认

合规系统中出现订单列表，订单系统中又出现咨诉列表；员工、客户、订单、素材和投诉信息分散在多个系统。页面相似不能证明它们共享同一接口、同一权限或同一更新时间。

尤其需要核实：

- 一个员工对应多个企微账号时使用什么稳定标识；
- 企微客户、订单用户、直播间用户和外部异常手机号如何关联；
- 相同咨诉记录在合规系统和订单系统中是否为同一流程 ID；
- 关闭、退款、拉黑等结果是否能反向同步。

### 问题 9：授权调阅和审计只是入口，尚未形成可验证的安全闭环

风险详情未来会聚合聊天原文、录音、证件、手机号、订单金额和投诉信息。当前虽然有授权调阅、部分掩码和企业筛选，但角色配置、字段级权限、跨企业隔离和查看/导出审计均未验证。

如果直接建设统一证据页而不先定义权限继承，AI 集成反而会扩大敏感信息暴露面。

## 5. 访谈需求与现有页面基础

| 访谈需求 | 当前系统证据 | 能力验证状态 | 主要缺口 |
| --- | --- | --- | --- |
| 准确识别投诉、退款、抱怨和外诉 | 词库、触发记录；退款预警有评分/置信度字段 | 存在候选输入与结果字段，识别效果未验证 | 上下文语义、实际模型、精度和评测未验证 |
| 一键查看客户完整上下文 | 员工/客户会话存档、查看上下文入口 | 存在相关入口，跨源聚合未验证 | 接口、数据覆盖和原始记录回跳未验证 |
| 风险自动形成任务并闭环 | 咨诉/违规列表有任务时间和多种状态 | 存在状态字段，真实闭环未验证 | 指派、延期、升级、复核权限和状态转换待验证 |
| 重复触发关联历史事件 | 有“查看历史”入口 | 事件关联能力未验证 | 是否按客户和事件聚合、复发机制不明 |
| 直播间风险通知相关人员 | 直播审核、通知配置、关联人员字段 | 页面相关性存在，二者联动未验证 | 客户—直播间—投顾—销售关系路由和通知时效不明 |
| 多模态素材审核及修改建议 | 素材、直播和股票审核入口 | 审核流程入口存在，内容理解能力未验证 | 图片/视频理解、风险定位、改写建议和版本链不明 |
| 客户风险分级并联动拦截 | 异常客户、等级、购买拦截标识、拦截记录 | 存在分类与记录展示，真实联动未验证 | 动态分级、解除机制、跨场景一致性和实时联动不明 |
| 员工多企微账号与组织映射 | 页面有企业/事业部/部门/员工筛选 | 组织筛选存在，多账号映射未验证 | 稳定员工 ID、多账号映射和历史变更不明 |
| 人工复核反哺模型 | AI 分析字段、处理入口 | 未观察到完整反馈入口，不能据此判定不存在 | 标注、评测集、版本管理、效果看板和回滚机制待核实 |
| 敏感证据权限和审计 | 授权调阅、部分掩码 | 存在权限设计线索，执行效果未验证 | 字段级权限、继承规则、查看/导出审计未验证 |

## 6. 哪些能力复用、优化或新建

| 当前能力 | 处置建议 | 原因 |
| --- | --- | --- |
| 员工/客户会话存档 | **优先验证的复用候选** | 验证生产主存、接口、数据完整性和回跳后，再确定是否作为原始聊天证据来源 |
| 授权调阅、导出 | **优先验证并强化审计** | 验证原权限关系和导出边界，同时评估字段级脱敏和访问留痕 |
| 关键词搜索、敏感词/行为 | **保留为召回层** | 适合低成本发现候选信号，但不能直接等同风险结论 |
| 退款预警 | **验证后合并到 AI 风险发现层** | 字段设计接近模型输出，但当前无数据、效果未知 |
| 咨诉列表、违规列表 | **保留业务流程，统一事件入口** | 已有任务状态雏形，新工作台应聚合而非复制 |
| 投诉处理 | **先核实业务语义** | 确认其与咨诉、预警的业务边界，再决定是否承载正式投诉登记 |
| 分类与词库 | **升级为规则治理** | 增加制度来源、场景、版本、阈值、生效区间和审批 |
| 通知设置 | **升级为路由策略** | 从静态接收人扩展为按客户关系、组织和风险级别动态路由 |
| 异常客户、外部异常客户 | **保留并接入风险画像** | 作为客户风险状态和外部名单来源，不直接替代风险事件 |
| 拦截记录 | **评估作为执行证据** | 已有客户、分类、场景和时间；命中规则、执行结果及解除记录待核实或补充 |
| 投顾/从业人员 | **复用资质信息，主数据归属待确认** | 不建议在多套系统分别维护同一员工身份 |
| 呼叫中心、订单列表 | **改为关联数据和深链** | 合规工作台只展示必要摘要，详情回原系统，避免重复建设 |
| 股票、素材、直播审核 | **保留流程，增加 AI 审核助手** | 原流程具备行业价值，AI 负责预审、定位和建议，不绕过人工责任 |
| 风险事件中心 | **核实现有对象后扩展或新建** | 当前未证明存在跨信号、跨渠道的统一事件对象，不能直接认定缺失 |
| 统一证据链 | **核实现有能力后扩展或新建** | 目标是汇总来源系统、对象 ID、快照及原始记录回跳，不重复业务主存 |
| AI 复核工作视图 | **作为同一任务的增强视图** | 模型、证据和建议同屏，但不维护第二份任务状态或最终裁决 |
| 模型评测与版本管理 | **核实后补建** | 若现有系统没有对应能力，再补充灰度、回归、回滚和持续学习 |

## 7. 原合规 SaaS、资产中心与 AI 风控层的职责边界

### 推荐关系

```text
企微 / 呼叫中心 / 订单 / 直播 / 素材系统
                    ↓
        数据资产中心：统一索引与关联
                    ↓
      AI 风控层：识别、聚合、解释与建议
                    ↓
原合规 SaaS：人工复核、任务执行、审核与拦截
                    ↓
        处置结果回流资产中心和评测集
```

### 职责表

| 系统 | 应负责 | 不应负责 |
| --- | --- | --- |
| 数据资产中心 | 结构化留存、稳定 ID、跨源关联、原始记录索引、权限继承、证据回跳 | 判断员工是否违规、直接批准退款、替代业务系统状态 |
| AI 风控层 | 意图识别、风险聚合、置信度、证据摘要、情绪与责任线索、处置建议 | 无人工或规则授权时直接处罚员工、拉黑客户或放行内容 |
| 原合规 SaaS | 人工复核、任务流转、通知、审核、拦截、监管留痕 | 再复制一套完整资产库或各源系统业务详情 |
| 订单/直播/素材等源系统 | 维护各自权威业务状态和执行动作 | 作为跨系统风险全貌的唯一入口 |

### 对象归属与唯一写入权

| 对象/字段 | 建议唯一写入方 | 其他系统的使用方式 |
| --- | --- | --- |
| 原始消息、订单、退款、合同、素材版本 | 对应源系统 | 资产中心保存来源 ID、必要快照、采集时间和更新时间；AI 只读分析 |
| 原系统规则触发记录 | 原合规 SaaS | 保留原记录 ID；AI 层只引用，不改写 |
| AI 衍生风险信号及模型输出 | AI 风控服务 | 关联原始证据，可重新计算，不覆盖源数据 |
| 风险事件 ID | 优先复用原合规 SaaS；若确认没有再由新服务维护 | 必须与原流程 ID 一一映射或明确主从关系 |
| 任务状态、责任人、截止时间 | 原合规 SaaS 的现有任务流（验证通过后） | AI 工作视图通过同一接口读取和办理，不另存第二套状态 |
| 人工复核结论、结案原因 | 原合规 SaaS 的授权复核动作 | AI 层只接收回流结果，用于评测和训练 |
| 模型反馈标签、评测结果 | AI 模型治理模块 | 引用事件 ID、流程 ID 和复核人，不替代业务裁决 |

若原合规 SaaS 的状态机验证不通过，应在架构评审时重新指定唯一任务主存；在此之前不能让新旧两套系统同时推进同一事件。

### 最重要的集成原则

1. **不复制业务真相**：订单、退款、合同等状态以源系统为准，资产中心保存索引、采集时间、来源更新时间和必要快照。
2. **不丢失来源**：所有 AI 结论都必须能关联消息 ID、会话、订单、素材版本或审核记录；同时记录证据版本或校验标识，以及缺失、过期、同步失败、已删除或无权访问状态。
3. **不绕过权限**：新页面的可见范围不得大于来源系统授权范围。
4. **不让 AI 直接定责**：模型提供风险、证据和建议；处罚、强制退款、拉黑和审核放行仍由授权人员确认。
5. **优先回写现有任务**：如果咨诉/违规列表已有可用状态机，AI 事件应通过接口创建或更新现有任务，而不是形成第二套孤岛。

## 8. 建议的 AI 集成后信息架构

不建议直接改动甲方原有 9 个一级模块。若验证确认原系统缺少统一工作入口，可以新增独立一级入口“AI 风控工作台”。首期应收敛为一个队列和一个详情，其他页面作为后续候选：

| 阶段 | 页面 | 主要解决的问题 | 与原系统关系 |
| --- | --- | --- | --- |
| 首期 | 待办队列 | 今日新增、待确认、即将逾期、待复核、复发和高危事件；客诉作为类型筛选 | 汇总原任务，不维护第二份状态 |
| 首期 | 统一事件详情 | 同一客户、同一问题的信号、证据、任务和历史复发 | 作为原任务的增强工作视图，通过同一接口办理和复核 |
| 后续候选 | 员工质检 | 高确定性违规、责任团队、整改和复核 | 聚合违规列表、会话与员工组织 |
| 后续候选 | 客户风险 | 当前等级、历史事件、标签、拦截与解除记录 | 聚合异常客户和拦截记录 |
| 后续候选 | 内容预审 | 股票、素材、直播的 AI 预审和修改建议 | 结果写回现有送审/审核流程 |
| 后续候选 | 规则与模型 | 制度规则、场景策略、模型版本、阈值和评测 | 扩展现有分类、词库和监控设置 |
| 后续候选 | 管理报表 | 本期发生、当前积压、团队风险、SLA、误报和复发 | 基于统一事件口径计算 |

其中“沟通记录、订单、退款、素材、人员”等完整数据仍应在资产中心或原业务系统中查看；AI 风控工作台只呈现完成判断所需的摘要和证据链。

## 9. 建议首期范围

### 首期应该做

1. 验证“咨诉列表”是否能够作为唯一任务承载对象；若不能，先完成任务主存和流程 ID 的架构决策，再开发 AI 工作视图。
2. 打通客户、员工、企微账号、消息和订单的稳定关联，先解决点击风险事件即可查看证据的问题。
3. 仅选择外诉、明确退费和高强度投诉三类高价值信号进行 AI 复判。
4. 建立风险信号、风险事件和处置任务三层数据关系，避免一条消息生成一个长期任务。
5. 提供统一事件详情：风险结论、命中依据、上下文、关联订单/退款、历史事件和处理建议同屏；页面通过原任务接口办理和复核，不自行维护状态或最终裁决。
6. 将人工“误判/确认、分类修正、证据选择、结案原因”沉淀为评测数据。
7. 形成最基础的管理指标：本期新增、当前积压、人工确认率、平均处理时长、逾期、复发。

### 首期暂不应该做

- 不一次性覆盖 180 万级历史触发记录；先做小范围回放和静默评测。
- 不立即把所有敏感词替换为大模型；词库仍可承担低成本召回。
- 不直接让 AI 自动处罚员工、强制退款、拉黑客户或放行素材。
- 不同时重做会话存档、订单、呼叫中心和素材管理。
- 不把管理看板建立在多套列表分别统计的基础上，应先统一风险事件口径。

| 优先级 | 验证项 | 通过标准 |
| --- | --- | --- |
| P0 | 咨诉/违规的真实状态机 | 能完成一次新增或触发、指派、处理、复核、延期/逾期、完结全过程，并拿到状态与时间字段 |
| P0 | 会话数据覆盖 | 明确支持的消息类型、同步延迟、失败补偿、历史期限和缺失比例 |
| P0 | 人员与账号关系 | 一个员工多企微账号可用稳定 ID 关联，组织变更保留历史 |
| P0 | 客户跨系统映射 | 企微客户、订单用户、直播间用户和手机号有明确匹配规则及冲突处理 |
| P0 | 权限继承 | 新页面按企业、组织、角色、客户关系和字段敏感度控制查看范围，所有访问可审计 |
| P0 | 首期责任路由与通知 | 针对首期外诉/退费/投诉渠道，能证明主责/协同人确定、通知送达、转派、处置时限和升级有效 |

## 11. 最大风险与最小验证

### 最大风险

最大的失败风险不是模型不够强，而是**没有统一风险事件和稳定身份关系时，就直接把 AI 结果塞进现有多个列表**。这样只会产生更多重复任务和更多人工核查，进一步放大当前的工作量问题。

### 最小验证方式

选择最近一段时间的外诉/退费相关记录，构造一个小规模脱敏且类别平衡的独立样本，必须同时包含真实风险、普通表达、非投诉抱怨、模糊样本、重复触发和已结案事件：

1. 由合规人员确认每个事件的客户、消息、证据、订单/退款结果和最终结论。
2. 验证能否通过现有页面或接口还原完整证据链，并记录缺失、过期和无权访问情况。
3. 用 AI 只做风险复判和证据摘要，不自动执行处置。
4. 分别比较误报、漏报、高危事件精度、平均取证时间、人工处理量和减少的无效任务，不能只报告笼统准确率。
5. 若证据自动聚合明显降低核查时间、且高危事件精度达到业务可接受标准，再扩展类别；如果连身份关联和证据完整性都无法稳定满足，应先暂停模型扩张，优先治理数据关系。

## 12. 最终建议

1. **保留原合规 SaaS，不做整体替换。**它已经承载大量业务入口和可能的流程状态，迁移成本与回归风险过高。
2. **先验证现有对象与状态机；确认缺口后再增加 AI 风控工作视图。**工作视图围绕风险事件和证据链，但不形成第二套任务状态。
3. **数据资产中心负责“找得到、关联得上、回得去”，原合规 SaaS 负责“有人处理、有人复核、结果留痕”。**
4. **首期只做客诉高危场景。**先验证准确识别、证据自动聚合和任务闭环，再扩展员工质检和素材审核。
5. **交互原型和 P0 系统事实核查可以并行。**原型中必须标明未验证假设；联调和上线前，P0 事实必须验证通过。

总体倾向：**值得继续，但必须从“增加 AI 功能”调整为“统一风险事件 + 证据链 + 复核闭环”的集成改造。**
