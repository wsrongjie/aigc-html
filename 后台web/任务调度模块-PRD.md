## 一、产品定位

任务调度模块是后台运营控制台的一部分，面向运营管理员和研发支持人员，用于**观察和管理**视频生成任务的 GPU 资源分配和排队情况。

**核心原则：**

- 调度模块只做资源分配策略配置和状态展示，不直接干预正在执行的租户任务
- 所有配置变更必须记录操作审计
- 底层调度逻辑由后端任务调度器执行，运营后台仅提供配置下发和可视化面板

### 4.3 GPU 分派规则

GPU 在首次调度时按顺序分派给队列：

1. 全部可调度 GPU 按 ID 升序排列
2. 前 N 张分派给 VIP 队列（N = VIP 基础并发数）
3. 接下来 M 张分派给普通队列（M = 普通基础并发数）
4. 多余的 GPU 标记为"未分派"

未分派的 GPU 不参与任何队列调度，可用于后续扩展或手动分配。

## 五、租户级最大并发

### 5.1 定义

每个租户独立配置"视频最大并发数"，在调度模块中按**最大运行并发**解释：控制该租户**同时占用 GPU 执行的视频生成任务上限**。

排队中的任务不消耗该并发额度。*若后续需要限制租户可提交/排队的任务总量，应单独增加"最大活跃任务数"（排队中 + 运行中），不要与本字段混用。*

| 字段      | 位置               | 调度口径    | 示例                |
| ------- | ---------------- | ------- | ----------------- |
| 视频最大并发数 | 租户管理 > 新建/编辑租户表单 | 最大运行并发数 | 雨虹投资: 10, 鑫源保险: 5 |

> 该字段已在租户管理中配置，调度模块直接读取使用。

### 5.2 与队列调度的关系

租户最大并发是一个**独立的过滤条件**，与同队列内的租户级轮询调度配合使用。

它不改变 VIP / 普通队列的资源隔离关系，也不改变单个租户内部任务的提交顺序；它只决定某个租户在本轮调度中是否还能继续获得 GPU 槽位。

```
队列选择（VIP 自有 / 普通自有 / VIP 借用）
           ↓
按租户轮询指针选择下一个租户
           ↓
检查该租户当前运行任务数是否已达上限
    ├─ 未达到 → 取该租户最早提交的任务，分配 GPU
    └─ 已达到 → 本轮跳过该租户，继续轮询下一个租户
```

同一个租户内部仍按提交时间 FCFS；不同租户之间采用轮询，避免某个租户一次性提交大量任务后长期占用同一队列资源。

典型例子：

> GPU 可用槽位 = 4。租户 A 最大并发 = 2，租户 B 最大并发 = 1，租户 C 最大并发 = 3，三者都存在待执行任务。本轮按 A → B → C → A 分配后，A 达到 2/2，B 达到 1/1，C 为 1/3。后续若仍有空闲 GPU，轮询到 A、B 时会因达到并发上限被跳过，C 可继续获得资源，直到达到自己的并发上限。

### 5.3 调度算法中的集成

调度算法的步骤 3（VIP 自有分配）、步骤 4（普通分配）、步骤 5（VIP 借用）中，每次分配 GPU 槽位时按租户轮询：

```
从当前队列的租户轮询指针开始:
    取下一个租户 T

    if T 的待执行队列为空:
        跳过 T
        continue

    if T 的当前运行任务数 >= T 的最大运行并发数:
        跳过 T
        continue

    从 T 的租户子队列中取最早提交的任务 t
    分配 GPU
    T 的当前运行任务数 +1
    轮询指针移动到 T 的下一个租户
```

### 5.4 GPU 卡片上的可视化

运行中的 GPU 卡片上，在租户名旁边显示并发饱和度：

```
GPU-01  ──────────  [VIP队列]
雨虹投资 · vt_201  │  运行 04:18
并发: 3/10 ███░░░░░░░    ← 新增
```

饱和度条视觉规则：

- ≤ 60% 蓝色
- 61% ~ 90% 橙色
- > 90% 红色
- 达到 100% 时显示"⚠ 已达上限"

### 5.5 等待列表中的体现

实时队列状态列表中，对于因达到租户并发上限而无法分配的任务，在"等待原因"列标注：

| 等待原因     | 说明                    |
| -------- | --------------------- |
| GPU 资源不足 | 队列内无空闲 GPU 槽位         |
| 等待轮询中    | 租户尚未在当前队列轮询中获得可用槽位    |
| 租户并发已达上限 | 有 GPU 空闲，但该租户已达到最大并发数 |

## 六、队列模型

### 6.1 两级队列架构

```
                    ┌─────────────┐
                    │  任务提交池   │
                    └──────┬──────┘
                           │
              ┌────────────┴────────────┐
              │                         │
     ┌────────▼────────┐     ┌─────────▼────────┐
     │   VIP 队列       │     │   普通队列         │
     │   高优先级       │     │   标准优先级       │
     │   基础并发: N    │     │   基础并发: M      │
     │   可借用: ✓/✗   │     │   保底并发: R       │
     │                  │     │                   │
     │   关联等级:      │     │   关联等级:        │
     │   · VIP客户     │     │   · 普通客户       │
     │   · 大客户       │     │   · 试用客户       │
     └────────┬────────┘     └─────────┬────────┘
              │                         │
              └──────────┬──────────────┘
                         │
                  ┌──────▼──────┐
                  │  GPU 集群    │
                  │  (K 张可调度) │
                  └─────────────┘
```

### 6.2 租户子队列模型

同一个资源队列内部不直接使用全局任务列表做 FCFS，而是按租户拆分为多个租户子队列：

```
VIP 队列
  ├─ 租户 A 子队列：A1 → A2 → A3
  ├─ 租户 B 子队列：B1 → B2
  └─ 租户 C 子队列：C1

普通队列
  ├─ 租户 D 子队列：D1 → D2
  └─ 租户 E 子队列：E1 → E2 → E3
```

调度规则：

- 租户之间：按 Round Robin 轮询，保证同一队列内多个租户公平获得资源
- 租户内部：按任务提交时间 FCFS，保证同一租户自己的任务顺序稳定
- 并发过滤：若某租户当前运行任务数已达到该租户最大运行并发，则本轮跳过该租户
- 空队列过滤：若某租户子队列为空，则本轮跳过该租户
- 轮询指针：VIP 队列和普通队列各自维护租户轮询指针；VIP 自有分配和 VIP 借用分配都使用 VIP 队列指针，普通自有分配使用普通队列指针

### 6.3 队列配置参数

| 参数   | 所属队列     | 类型  | 默认值   | 说明                   |
| ---- | -------- | --- | ----- | -------------------- |
| 基础并发 | VIP / 普通 | 整数  | 4 / 3 | 该队列独占的 GPU 数量        |
| 允许借用 | VIP      | 开关  | 开启    | VIP 队列是否允许借用普通队列空闲资源 |
| 保底并发 | 普通       | 整数  | 1     | 普通队列保留的 GPU 数，不可被借用  |

**校验规则：**

- VIP 基础并发 + 普通基础并发 ≤ 可调度 GPU 总数
- 保底并发 ≤ 普通基础并发

### 6.4 队列状态指标

每个队列卡片实时展示：

| 指标   | 说明             |
| ---- | -------------- |
| 基础并发 | 该队列独占的 GPU 数量  |
| 运行中  | 正在执行任务的数量（含借用） |
| 排队中  | 等待执行的任务数量      |
| 平均等待 | 该队列任务平均等待时长    |

### 6.5 队列槽位可视化

每个队列下方展示并发槽位示意图：

**VIP 队列槽位：**

```
[①] [②] [③] [④]  ── 蓝色，运行中
[⑤] [⑥] [⑦]       ── 橙色，从普通借入的资源
```

**普通队列槽位：**

```
[①] [②]           ── 绿色，运行中
[③]                ── 绿色虚线，保底槽（空闲）
[④]                ── 白色虚线，空闲（可被借用）
```

图例说明：

- 蓝/绿实心 = 运行中
- 白色虚线 = 空闲
- 橙色实心 = 被 VIP 借用
- 绿色虚线 = 保底槽

## 七、调度策略

### 7.1 调度算法流程

```
输入：按队列/租户分组的待调度任务、GPU 状态、队列配置、租户当前运行并发
输出：本轮新增的 GPU 占用分配

基本原则：
  - 运行中任务不可抢占，不因重新调度而被中断或迁移
  - 重新调度只处理空闲 GPU 槽位与待执行任务
  - 同一资源队列内采用租户级 Round Robin
  - 同一租户内部按任务提交时间 FCFS

步骤 1 — 读取 GPU 状态
  排除 maintenance / fault GPU
  保留 running GPU 的现有任务绑定
  仅 idle GPU 进入本轮可分配资源池

步骤 2 — GPU 分派
  按顺序分派：前 N 张给 VIP，接下来 M 张给普通，多余标记为未分派

步骤 3 — VIP 自有分配
  使用 VIP 队列的租户轮询指针
  对 VIP 自有空闲 GPU 槽位逐个分配任务
  若租户为空队列或达到最大运行并发，则跳过该租户

步骤 4 — 普通分配
  使用普通队列的租户轮询指针
  对普通自有空闲 GPU 槽位逐个分配任务
  普通保底并发只限制 VIP 借用，不限制普通队列自用

步骤 5 — VIP 借用（软隔离）
  条件：
    a) VIP 允许借用 = 开启
    b) VIP 仍有等待任务（自有 GPU 已用完）
    c) 普通队列有空闲 GPU（超出保底并发部分）
  动作：
    按 VIP 队列的租户轮询指针选择等待任务，依次占用普通队列空闲 GPU
    被占用的 GPU 标记为 "借用" 状态
  限制：
    保底并发的 GPU 不参与借用

步骤 6 — 归还
  每次重新调度时只重新计算空闲槽位：
    a) VIP 等待队列清空 → 空闲的借用槽位归还
    b) VIP 等待队列缩小 → 未被运行任务占用的多余借用槽位归还
    c) 普通队列排队长度不影响已借出的 GPU（不主动回收）
    d) 已借用且正在运行的 VIP 任务自然完成后，GPU 回到普通队列空闲池
```

租户轮询伪代码：

```
tenantRoundRobin(queueId, idleSlots):
    for slot in idleSlots:
        scanned = 0

        while scanned < 当前队列租户数:
            T = 从 queueId 的轮询指针取下一个租户
            scanned += 1

            if T 的待执行任务数 == 0:
                continue

            if T 的当前运行任务数 >= T 的最大运行并发数:
                continue

            task = 从 T 的子队列取最早提交的任务
            将 task 分配给 slot
            T 的当前运行任务数 += 1
            轮询指针移动到 T 的下一个租户
            break

        如果扫描一整圈仍没有可调度租户:
            停止为该队列继续分配
```

### 7.2 调度触发时机

（后端实现，运营后台仅做配置下发和展示）

| 触发时机    | 说明                      |
| ------- | ----------------------- |
| 新任务提交   | 任务进入排队池，触发调度器重新分配       |
| 任务完成    | 某 GPU 上的任务完成，触发调度器重新分配  |
| 任务失败/取消 | GPU 释放，触发调度器重新分配        |
| 配置变更    | 管理员保存队列配置，触发调度器按新参数重新分配 |

### 7.3 同一队列内的任务排序

同一资源队列内采用两层排序：

1. **租户之间**：按 Round Robin 轮询，避免单个租户批量提交任务后长期占用资源
2. **租户内部**：按提交时间 FCFS（先到先服务）

> MVP 阶段同一队列内不做租户等级加权，统一采用普通 Round Robin。后续如需区分合同等级，可升级为加权轮询 WRR，例如高等级租户权重 3，普通租户权重 1。

## 十、借还逻辑总结

### 10.1 借用条件（同时满足）

1. VIP 允许借用开关开启
2. VIP 队列有等待任务（VIP 自有 GPU 用完）
3. 普通队列有空闲 GPU（超出保底并发数）

### 10.2 借用范围

可借用的 = 普通队列空闲 GPU - 保底并发数

例如：普通基础并发 3，保底 1，当前空闲 2
→ 可借用 1（2 空闲 - 1 保底）

### 10.3 归还条件（任一满足）

1. VIP 等待队列清空 → 未被运行任务占用的借用槽位全部归还
2. VIP 等待队列缩小，所需并发数减少 → 空闲的多余借用槽位归还，已运行任务不抢占
3. 借用的 GPU 上任务自然完成 → GPU 回到普通队列空闲池

### 10.4 不触发归还的场景

- ❌ 普通队列开始排队，但借出的 GPU 仍在运行 VIP 任务
- ❌ 管理员修改队列配置，但借出的 GPU 仍在运行 VIP 任务；新配置只影响空闲槽位和后续任务分配

## 十一、配置保存与审计

### 11.1 保存流程

1. 前端校验通过
2. 生成变更前后对比（如："VIP 4→5 / 普通 3→3 / 保底 1→2 / 借用开启"）
3. 写入审计日志
4. 更新本地调度配置
5. 触发调度器重新分配
6. 弹出 toast 提示"任务调度配置已保存"

### 11.2 审计日志

每次保存写入一条审计记录：

| 字段   | 内容示例                       |
| ---- | -------------------------- |
| 时间   | 2026-07-06 14:30:00        |
| 操作人  | admin                      |
| 类型   | 配置                         |
| 操作对象 | 任务调度配置                     |
| 变更前  | VIP 4 / 普通 3 / 保底 1 / 借用开启 |
| 变更后  | VIP 5 / 普通 2 / 保底 1 / 借用开启 |
| 备注   | 调整队列基础并发与软隔离规则             |

## 十二、边界与异常处理

### 12.1 GPU 故障或下架

- 对应 GPU 标记为 maintenance / fault
- 该 GPU 上运行的任务按任务状态机处理（失败或重新排队）
- 可调度总数动态减少，超出部分的任务进入等待队列

### 12.2 配置冲突

- VIP 基础 + 普通基础 > 可调度 GPU → 保存按钮禁用，显示错误提示
- 保底 > 普通基础 → 保存按钮禁用，显示错误提示

### 12.3 无可用 GPU

所有可调度 GPU 繁忙时：

- 新提交任务直接进入等待队列
- 队列卡片上排队中数量增加
- 不丢弃任何任务

### 12.4 空队列

- 队列无任务时：运行中 = 0，排队中 = 0，槽位全部标记为空闲
- 仍然占用基础并发的 GPU 数量（独占保留）
